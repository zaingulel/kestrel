# Session status and weekly usage research

Research record for [#123](https://github.com/zaingulel/kestrel/issues/123), checked on 21 October 2026, with owner-authorized external account/daemon observations at 19:03 Coordinated Universal Time (UTC), desktop live-status observations at 19:22–19:23 UTC, Claude/Omarchy tests recorded at 20:16 UTC, and owner-authorized, independently bootstrapped native desktop status/wait observations at 21:28–21:30 UTC. The question set is [the owner's wording](https://github.com/zaingulel/kestrel/issues/18#issuecomment-6301485706) and [the accepted additions](https://github.com/zaingulel/kestrel/issues/18#issuecomment-6301560379).

Standalone desktop status access is positively proven for one controlled local Codex chat on installed desktop `26.1013.40934`: an independent Python client registered its own identity through the native interprocess communication (IPC) router and observed working, native input-wait, native approval-wait and idle states. Separate native app observations confirmed the waiting flags, turn states and return to idle. This is a different private route from the actual Claude app-tools Model Context Protocol (MCP) call, which still failed for missing executor thread metadata. The IPC route receives full conversation objects before filtering; it is not a supported status-only interface or an installed Kestrel integration. Omarchy's existing Claude/Codex aggregate allowance caches remain usable with the freshness limits below, without a new Claude status-line installation. Claude's own inventory identified a busy job, but its waiting transitions remain unverified.

**Evidence labels:** **Supported** means an official interface contract; **Observed** means a bounded laptop probe; **Inferred** means the stated conclusion drawn from those facts; **Unavailable** means this investigation did not establish the capability. These are research findings, not an installed integration or permission to build one.

## Claude Code routes

**Supported:** `claude agents --json --all` is the documented external status read. Entries include `kind: interactive` or `background` and can expose identifiers, names, directories, start times, process IDs, process `status`, background-job `state` and `waitingFor`. Process status separates `busy`, `waiting` and `idle`. The five waiting reasons are `permission prompt`, `input needed`, `sandbox request`, `worker request` and `dialog open`. A background job can also be `blocked` without a live prompt/process, for example by an expired login; absence of `waitingFor` does not prove no attention is needed. Background states separate `working`, `blocked`, `done`, `failed` and `stopped`. A finished turn awaiting a new instruction is `done`, not `blocked`. State files beneath the Claude configuration directory are explicitly unstable interfaces. [Agent-view contract](https://code.claude.com/docs/en/agent-view#read-session-state-from-a-script).

**Documented scope versus observation:** the JavaScript Object Notation (JSON) contract says every live session and explicitly includes `interactive`; version-history entry `2.1.196` also names interactive sessions in `claude agents --json`. The screen's exclusion of other foreground terminals does not narrow that JSON contract. Subagents and teammates are not separate agent-view rows, and `CLAUDE_CONFIG_DIR` separates instances. Earlier restricted empty JSON results remain unexplained. A later host command returned populated interactive sessions including an owner-known busy job; this establishes that bounded observation, not a causal fix or universal coverage. Populated background and waiting transitions remain unverified. Re-read after disconnection; failed or unexplained empty observations cannot establish laptop-wide quiet. [JSON inventory](https://code.claude.com/docs/en/agent-view#list-sessions-as-json), [version evidence](https://code.claude.com/docs/en/agent-view#version-history), [instance separation](https://code.claude.com/docs/en/agent-view#where-state-is-stored).

**Supported usage feed:** a status-line command receives `rate_limits.seven_day.used_percentage` and `resets_at`; remaining percentage is `100 - used_percentage`. This requires a configured local command and applicable claude.ai subscription. The fields arrive only after the first application programming interface (API) response; individual windows can be absent and expire when their reset time passes. Status-line execution itself uses no API tokens. The input also carries directories, model, context and cost metadata, so any future collector must select only needed fields. Updates are event-driven unless a refresh interval is configured; rerunning a script does not prove the backend allowance was freshly fetched. Reading an already-populated feed need not issue a new model request. The first-response dependency concerns this machine feed; it does not establish that human `/usage` requires inference. No status-line configuration or model request was created for that status-line feed; the subsequent authorized cache-read test is recorded below. [Status-line data and lifecycle](https://code.claude.com/docs/en/statusline#available-data).

**Supported human fallback:** `/usage` shows plan limits, session cost and activity. It is an in-session command, not an established standalone machine interface. **Unavailable:** no supported Claude banked-reset count or standalone vendor weekly-usage query was established. The installed Omarchy cache below provides a separate local aggregate route. [Command reference](https://code.claude.com/docs/en/commands).

**Supported but excluded from the recommendation:** hooks can observe lifecycle and tool events if installed. Notification `permission_prompt` and `idle_prompt` are delayed and conditional; `idle_prompt` means the response ended, not that Claude asked a question. `AskUserQuestion` and permission requests are distinct events. Hook payloads may expose transcript paths, tool inputs and notification text; missing events or process death defeat an events-only inventory. Installing hooks would change configuration and is outside this research. [Hooks reference](https://code.claude.com/docs/en/hooks#notification).

### Status line versus the undocumented usage endpoint

**Observed locally, installed Omarchy `4.0.6-1` source:** the endpoint behind Omarchy's Claude allowance cache is the undocumented `https://api.anthropic.com/api/oauth/usage` (`/usr/share/omarchy/bin/omarchy-agent-usage-claude` line 36). The collector reads Claude Code's saved login token from `~/.claude/.credentials.json` (line 586) and sends it with the beta header `anthropic-beta: oauth-2025-04-20` (line 716); the endpoint can refuse checks with status 429 (line 725). It is not in Claude Code's documentation, so its shape, header and limits can change without notice. The collector was read, not run.

| | Documented status line | Undocumented usage endpoint |
|---|---|---|
| Grounding | **Supported:** `rate_limits.seven_day` in the status-line input | **Observed:** installed Omarchy source only |
| Needs | A status-line command added to Claude Code settings, and a live session that has had a model response | Claude Code's login token and a network request per check |
| Exposes to Kestrel | Weekly used percentage and reset time, beside directories, model, context and cost fields to discard | Weekly and other windows; whoever calls it holds a credential |
| Freshness | Updates on session events; absent when no session runs | Current on each request, but rate limited |
| Banked resets | Not provided | Not read by Omarchy's collector; the endpoint's full response was not observed |

**Recommendation:** Kestrel should not call the endpoint or read the credential file itself, because that puts a login token inside Kestrel and depends on an interface Anthropic has not published. It should not install a status line either, because that changes Claude Code's configuration and gives nothing when no session is running. Read the cache Omarchy already writes, as below: Kestrel then holds no credential and adds no requests. That cache inherits the endpoint's instability, and the record does not show a status-code refusal such as 429 when older limits exist (only a transport failure sets `retryAdvised`, collector line 840, and sign-in problems appear in `usageStatusText`, lines 811 and 815), and it does not show when the figures were fetched: when a check fails and older limits exist, the collector keeps those limits with a blank `usageStatusText` (`omarchy-agent-usage-claude` lines 840 to 845), and its fetch time lives only in Omarchy's private probe cache (line 834). Every figure must therefore be reported as last known, with freshness unknown, unless an approved plan also reads that undocumented probe cache. A missing cache is reported as unavailable, and the documented status line is the fallback if the owner later approves that configuration change.

## Installed Omarchy allowance route

**Observed locally:** the installed Agents panel reads aggregate provider records from `~/.local/state/omarchy/agents/usage/claude.json` and `~/.local/state/omarchy/agents/usage/codex.json`, both mode `0600`. The coordinator and an actual Claude Opus reviewer independently read selected fields; Claude used `jq`. Neither read triggered refresh or network access. Records contain named limits and reset timestamps; `percent` is the fraction **used**, so remaining percentage is `(1 - percent) * 100` only for a valid, usable window. No private values are reproduced. The records also carry the plan tier, prompt and session counts, per-model token counts and active dates (Claude collector lines 892 and 899; Codex collector lines 552 to 553, 597 and 598). Per-day `recentDays` entries use a `messageCount` key that holds token totals from local session scans (Claude collector lines 187 to 189; Codex collector line 129), so it is not a message count. A reader should keep the named limit's percentage, reset time and status fields (`usageStatusText`, `authHelpText`, `retryAdvised`); discard the activity counts. Installed source grounding is the Agents plugin's `Panel.qml` (lines 70, 235, 617, 738), `Main.qml` (117), `manifest.json` (20) and `README.md` (39), under `/usr/share/omarchy/shell/plugins/agents`. Fireworks is also enabled by default and a generic provider-cache contract exists, but no other-provider cache read was tested. This widget supplies aggregate usage, not live session status.

**Freshness limit:** `updatedAt` records collector assembly, not a verified backend fetch time. The installed shell updates every 15 minutes, and collectors can use network/authentication when refreshed; this research only read existing caches. Claude's collector can reuse a successful probe for 15 seconds, retain old limits after failure without an explicit stale error, and display expired windows as zero used. A recent timestamp or blank `usageStatusText` therefore does not establish fresh quota; expired zero must not become 100% remaining. Without usable cache data, messages can report waiting for authentication, expired sign-in or unavailable limits. The source findings came from Claude collector lines 797, 823, 885 and Codex collector lines 521, 574, 589. The Codex collector launches a separate standard-input/output app-server for account reads, which does not establish ownership of desktop turns. Reuse this installed aggregate route with truthful freshness limits; do not scrape credentials or rebuild its native collector.

## Codex server ownership, status and usage

**Supported protocol:** `thread/list` pages stored threads; `thread/read` reads without resuming or subscribing; `thread/loaded/list` lists the reached server's loaded threads. Initialization is required. The external test reached an already-running managed daemon and read stored desktop-chat metadata, but its live status disagreed with the app. Starting an independent app-server would not establish desktop live-state ownership. [App-server thread reads](https://learn.chatgpt.com/docs/app-server#threads).

**Supported transport, positively observed:** the standard Unix control socket accepts WebSocket handshakes. The installed `codex app-server proxy` copies bytes between standard input/output and the socket; it does not supply a WebSocket upgrade. Earlier raw-JSON attempts therefore did not perform a valid protocol initialization and do not establish daemon absence or external-read unavailability. The corrected bounded test used the installed `websockets 17.2` Unix client, completed `initialize` and then sent `initialized`, without launching a server. [Unix socket WebSocket acceptance](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-transport/src/transport/unix_socket.rs#L168), [proxy byte relay](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/stdio-to-uds/src/lib.rs#L8).

**First-party source, pinned to the observed CLI release:** OpenAI's annotated tag `rust-v0.163.0` resolves to immutable commit `83086188ae0614bd882818ff1aa23f3194962012`. The cited construction, thread-read and schema behavior was inspected at that revision. This matches the observed CLI version; the desktop app's bundled server version remains unverified. [Release tag](https://github.com/openai/codex/tree/rust-v0.163.0). Each message processor constructs its own watch manager; that manager holds runtime facts in memory and returns `notLoaded` for an unknown thread. Thread reads combine persisted metadata with that processor's loaded state. **Inferred:** a separately launched server can see persisted history without knowing another process's live turn. Its `notLoaded` result must not become “the desktop job stopped.” [Processor construction](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/message_processor.rs#L399), [runtime ownership](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/thread_status.rs#L306), [thread read](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server/src/request_processors/thread_processor.rs#L2960).

**Observed private desktop route:** installed desktop `26.1013.40934` source in the app archive's `main-CLu1A25j.js` and `src-DsLVGakC.js` was independently traced by the read-only explorer. The app's private app-server child communicates with main over standard-input/output socket pairs, separately from the daemon. Main exposes an owner-only `0600` Unix socket under the temporary `codex-app-tools` directory. Its JSON remote procedure call framing uses a four-byte little-endian length followed by UTF-8 JSON, capped at 8 MiB. `tools/list` routes to the live window's `requestDynamicToolsForThreadStart`; `tools/call` routes to `windowContext.callDynamicAppTool`. The packaged codex-app-tools plugin relays MCP standard input/output over this socket and converts native `contentItems` with `inputText`/`text` and `success` into MCP results. This is installed private implementation evidence, not a public vendor-supported stable external API.

**Observed access and limits:** an external one-off Python Unix-socket client listed the tools, then called `codex_app.read_thread` and `codex_app.list_threads` successfully. Calls carried namespace, tool, arguments, caller source, call identifier, thread/turn context and host. Genuine current chat and turn metadata came from a native app read; context-free attachment through this app-tools route from an independently launched Claude process remains unestablished. The independently bootstrapped IPC route below is a separate path. Linux peer authorization accepts the connection, with filesystem ownership permissions gating socket access. The catalog also exposes mutating tools, so a future approved connector would need to expose only permitted reads; no connector or enforcement was built here. The catalog advertised `get_usage_limits`, but no usage read through this socket was tested. The earlier daemon/account usage result remains separate evidence.

**Actual Claude native relay test:** the installed unmodified codex-app-tools MCP server and launcher connected using temporary per-process configuration; the parent also completed MCP initialization and tool listing. Earlier attempts were declined before tools, lacked the reviewer tool grant, or were blocked by plan-mode permission checks before dispatch. Those are not transport failures. In the final configured Opus reviewer attempt, the exact native `read_thread` tool was present and preapproved, no permission denial occurred, and the actual tool returned `MCP error -32602: Codex app tools require thread metadata from the executor.` No status fields returned. No metadata was fabricated or substituted from an interaction-client identifier. This tests the native Claude bootstrap gap: socket/MCP configuration alone is insufficient, while the earlier Python read with genuine supplied context remains valid. This app-tools route still lacks executor context. The separate IPC proof below resolves standalone connection feasibility for the controlled Codex chat without repairing the MCP route; no production adapter was built.

**Supported status distinctions:** `active` can carry `waitingOnApproval` or `waitingOnUserInput`. `idle`, `notLoaded` and `systemError` are separate states. The first two are not completion receipts. Turn statuses separately distinguish `inProgress`, `completed`, `interrupted` and `failed`. A prose question at the end of a completed turn need not be a live input request. [Thread status schema](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/schema/typescript/v2/ThreadStatus.ts), [waiting flags](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/schema/typescript/v2/ThreadActiveFlag.ts), [turn status](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/schema/typescript/v2/TurnStatus.ts).

**Supported usage read:** this is an account-scoped capability, independent of which server owns a desktop turn. The external default-account read succeeded; selecting the intended account/bucket and reporting observation age remain required. A matching in-app quota snapshot supports consistency but does not prove exact account identity: `account/read` exposed no stable account identifier in this observation. `account/rateLimits/read` returns quota windows, possibly several buckets, and optional earned-reset credits. Use `usedPercent`, `windowDurationMins` and Unix-seconds `resetsAt`. Identify a weekly window by duration, not by assuming it is always `secondary`; remaining is `100 - usedPercent`. Prefer the multi-bucket response where provided. `rateLimitResetCredits.availableCount` is authoritative; detail rows can be capped, absent details are not zero, and reset credits differ from purchased monetary credits. Missing fields are unavailable. A reset timestamp or low percentage alone does not establish permission to continue using the service. [Account-read contract](https://learn.chatgpt.com/docs/app-server#6-rate-limits-chatgpt), [window schema](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/schema/typescript/v2/RateLimitWindow.ts), [account response](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/schema/typescript/v2/GetAccountRateLimitsResponse.ts), [reset-credit summary](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/app-server-protocol/schema/typescript/v2/RateLimitResetCreditsSummary.ts).

## Independently bootstrapped native desktop IPC

**Observed registration and ownership:** an independent Python client connected to the installed desktop router at `~/.codex/ipc/ipc.sock`, initialized honestly as `kestrel-status-research` and received its own router-issued client identity. It did not impersonate an existing executor or borrow caller context; the exact diagnostic thread identifier was supplied as its explicit target. Discovery was scoped to the exact authorized diagnostic chat, rather than a full inventory. The archived `notLoaded` fixture initially had no owner; after diagnostic-only unarchive and a harmless native message, owner discovery succeeded. The executed reader put `targetClientIds` inside broadcast `params`, but the installed router's `handleBroadcast` reads that field from the outer envelope. Its follow and unfollow broadcasts therefore reached other registered clients; the `conversationId` remained exactly the authorized synthetic chat, and no other owner's conversation was followed or read. Each read still received a full snapshot in memory, emitted only selected status/configuration metadata and closed its socket. No raw snapshot was retained. No unsubscribe acknowledgment exists; follower removal on disconnect is source-defined and was not independently inspected in the owner's follower map. A future adapter must put the discovered owner in the outer `targetClientIds` and verify the snapshot's `sourceClientId` before using it.

**Installed source, not public IPC documentation:** in `/usr/lib/chatgpt/resources/app.asar`, `/.vite/build/application-network-startup-DB1VeU3v.js` functions `Fc`, `Uc`, `Wc` and `Vc` define endpoint resolution, ownership checks and four-byte little-endian JSON framing. `/.vite/build/src-DsLVGakC.js` implements `initialize` (version 0), `findThreadOwner` / `thread-owner-discovery` (version 1), `thread-stream-following-changed` (version 1) and `thread-stream-state-changed` snapshots (version 11). Its normalization function `ah` preserves the conversation object; `handleClientStatusChanged` removes disconnected followers. `/.vite/build/main-CLu1A25j.js` contains the transport adapter. These are version-bound private source citations, not a public stable API contract. The snapshot transfers conversation history and tool content before client filtering, even when only status fields are retained. The source also defines revisioned patches, but this test used fresh snapshot reads and did not prove long-lived patch or reconnect correctness.

**Observed native input-wait:** the separate fixture controller changed only the authorized test chat to Plan mode and user review through `thread-follower-update-thread-settings` version 2. It used the canonical Plan mask from the public daemon's `collaborationMode/list`, without inventing a mode object. At 21:28:40 UTC, independent IPC reported `active` with empty flags. At 21:28:44, native `wait_threads` reported `active[waitingOnUserInput]` with turn `inProgress`; independent IPC matched the waiting flag and contained a pending `item/tool/requestUserInput` with `isBlocking` and `autoResolutionMs` field names. No answer was sent. The exact fixture-turn interrupt used `thread-follower-interrupt-turn` version 4 with the actual `expectedTurnId` and `mode:user-stop`; it succeeded. Native observation then showed interrupted/idle, and IPC showed idle with empty requests.

**Observed native approval-wait:** the controller next set the fixture to default mode, `approvalPolicy:on-request` and `approvalsReviewer:user`. A harmless native prompt requested only `/usr/bin/true` with `require_escalated`. At 21:29:26 UTC, native `wait_threads` showed `active[waitingOnApproval]` with turn `inProgress`; independent IPC matched the waiting flag and contained a pending `item/commandExecution/requestApproval`. No approval grant was sent. The exact-turn interrupt succeeded, native observation showed interrupted/idle, and IPC returned idle with empty requests. This proves the native waiting state, not execution of the requested command or successful tests. Public app-server documentation and schemas explain status and approval semantics; they do not document this private router. [App-server status and approval contract](https://learn.chatgpt.com/docs/app-server).

**Restoration and provenance:** reapplying the original settings succeeded, but strict equality of the entire `latestThreadSettings` object failed. After one harmless tools-forbidden confirmation turn, the only difference key was `summary`; its cause was not established. The deliberately changed selections were confirmed restored: default mode, `auto_review`, `on-request`, the same model/effort and unchanged sandbox. Native confirmation completed and IPC was idle at 21:30:38 UTC. The fixture was archived again and all one-off reader/controller processes exited. These native-tool, controller and cleanup receipts are supplied by the coordinating conversation. The private eight-row metadata JSON Lines (JSONL) file corroborates IPC states and selected settings only; it does not independently prove the native counterpart, cancellation, archive or socket closure. No whole-object exact restoration is claimed.

**Recovery limit:** this proves independent registration and native Codex waiting-state feasibility for one controlled local chat. It does not prove failed/`systemError` transitions, all-host inventory, remote or ChatGPT Work-mode coverage, production security enforcement, or upgrade compatibility. Live notifications require the owning connection/subscription; history reads do not subscribe. A future adapter must reconcile fresh state after missed events or reconnect before answering “since last checked,” and report stale/unavailable data explicitly. No supported read-only desktop-wide event subscription was established. Human Activity view remains a fallback, not an external event API.
